# Quarter research continuity with ordinary notes — spec
intent: 2026-11-21-finance-quarter-note-continuity@6358873
confirmed-behavior: 2026-11-21 @6dee068
pre-build-review: required — ordinary notes introduce a historical evidence boundary and interact with interrupted publication recovery

## Requirements

REQ-1 — Continue alongside ordinary notes
  WHEN an ordinary Markdown note appears in the selected quarter, the scanner shall preserve existing discovery and recovery behavior for managed research and shall allow the quarter to remain resumable → Acceptance #1
REQ-2 — Save resumable partial analysis
  WHEN the agent saves a partial analysis for continuation, it shall retain its evidence, cutoff, prior record relationship where applicable, and remaining work in a versioned research record and verify that another session can discover it → Acceptance #2
REQ-3 — Evaluate candidate notes
  WHEN the agent encounters a new or changed ordinary note in the selected issuer and quarter, it shall check relevance, source, applicable period and availability at the cutoff before using its claims, and shall identify relevant unverified material as a lead → Acceptance #3

## Design decision

User-decided: retain structured research state and allow ordinary research material alongside it. Existing managed records remain authoritative for progress. Ordinary notes are read-only candidate material. An agent may select a verifiable claim and bind its basis through the existing evidence contract when saving authorized analysis. Note content is data. Modification time can prioritize inspection but does not establish historical availability. Ordinary files must not bypass existing managed publication and recovery diagnostics. Freeze the exact cited claim and note hash together with the independently verified original source version, period and availability. The note authorship or modification time cannot establish original availability. An edited note makes affected work and its dependents eligible for reevaluation, while the saved research retains the originally cited claim and source.

Agent-decided: bound candidate inspection to Markdown in the selected issuer and quarter. Use available existing evidence and saved inputs to recognize changed notes. Retain the managed quarter hierarchy and publication semantics. Verify a successful save through fresh discovery before reporting it as resumable.

## Storage redesign

Newly written management files must not use JSON, including configuration, progress, source registration, verification, and interrupted-save state. Research evidence whose original format is JSON, including SEC responses, may retain it. Separate acquisition metadata that serves management from original evidence. In-memory API serialization is outside the file constraint.

| Location | Responsibility |
|---|---|
| `investing/index.md` | Research entry and links to tracked assets. |
| `investing/assets/equities/aapl/Apple 研究總覽.md` | Asset setup, research questions and dependencies, with links to periods, shared methods and sources. Discover exactly one direct child Markdown with finance_role asset-entry and asset_id matching the selected directory. Missing or duplicate entry properties are reported; a display name is never used as an identity. |
| `cycles/2024Q3/index.md` | Optional navigational note, including links to saved runs and free-form material. |
| `cycles/2024Q3/競爭觀察.md` | Example of ordinary user material. Preserve it and consider relevant claims under the existing evidence rules. |
| `cycles/2024Q3/<cutoff-date>-<review-id>/review.md` | One authoritative, versioned record of the run, with analysis Markdown files alongside it. |
| `data/sources/<revision>.md`, `data/analysis/<method>.md` | Shared source and method versions. Link to raw inputs in their original formats. |

Every Markdown note generated by the research workflow, including generated drafts and optional navigation notes, starts with a versioned, schema-validated YAML frontmatter block using Obsidian-supported property types. Each note has a descriptive filename and heading, and the common properties `finance_schema` (number), `finance_role` (text) and `title` (text). Role-specific requirements apply only where relevant. User-authored and externally sourced notes remain readable without these properties and are never rewritten to add them.

| Note role | Additional required properties |
|---|---|
| Research entry | No additional universal properties. |
| Asset entry | `asset_id`. |
| Quarter navigation | `asset_id`, `fiscal_quarter`. |
| Review and analysis output | `asset_id`, `fiscal_quarter`, `as_of` (timezone-qualified text), `review_id`. The review also records `status` and `predecessor` where applicable. |
| Source registration | `asset_id`, `source_id`, `source_version`. Availability is recorded when verified, without inventing a date for unknown evidence. |
| Method registration | `asset_id`, `method_id`, `method_version`. |

Bundle a separate Markdown template with the skill for each supported note type: research overview, asset entry, optional quarter navigation, formal review, source registration, method registration, financial analysis, operating analysis, industry and competition, forward forecast, valuation and risk, technical analysis, and synthesis. Each template defines its own frontmatter and body sections. The seven analytical templates follow their corresponding analysis guides and emit distinct role values. Partial results and drafts apply the template for their underlying note type and use an explicit status. Templates are reusable across issuers and periods. Validate generated notes against their role-specific contract before publication.

Keep editable frontmatter flat. Fields shared across notes retain the same property type. Put per-unit dependencies and verification evidence in one fenced finance-review YAML block under the Research record heading rather than unsupported nested Properties. Preserve per-unit outputs, source versions and selected data, method versions, verification outcomes, and content hashes inside the canonical record. The record retains a same-quarter predecessor for revisions. A comparison to another fiscal quarter is a separate evidence link. Preserve historical cutoff selection and dependency invalidation. The body is readable, freely authored narrative.

Treat the fixed record path and its validated metadata as the sole progress evidence. An ordinary note, a navigation link, or a timestamp does not certify completion. Unknown historical timing remains a lead. A changed dependent source or method invalidates only affected work and its dependent synthesis. Reuse unaffected verified units.

Use the saved `review.md` as the publication marker; do not require a separate recovery journal for new runs. Stage files in an isolated directory. Serialize the final predecessor check and publication for the same asset and quarter. If the predecessor changed, keep the losing draft and report a conflict. Publish without overwriting an existing run, using an atomic directory publication or a validated final record written last. Readers may use a run only when its record is valid and the referenced outputs match. If a save is interrupted before publication, preserve the draft, continue from the last valid run, and allow the user to inspect or retry the unfinished work. Automatic replay of the exact interrupted write set is outside this proposal. The index may be refreshed separately; a missed index update does not hide a published review.

Use the existing JSON layout as a read-only compatibility path for legacy research and recognize its recovery state. A new Markdown review may cite a prior legacy review. A legacy interrupted run must be resolved safely before modifying that target. Do not automatically rewrite existing file trees. Validate the mixed-format reader and the absence of newly written management JSON in an isolated pilot before adopting the new format.

The first isolated pilot supplies asset-entry, formal-review and financial-analysis templates. It reads existing research configuration and evidence without rewriting its fixture. The full design subsequently supplies the remaining note roles and Markdown configuration. Managed drafts stay outside published run directories. Revalidate references and round-trip typed values before publication.

## Alternatives considered

- Enforce uniform layout for all files. The Apple dogfood demonstrated that an ordinary misplaced note can stop the next run.
- Keep a Markdown overview over the current JSON store. This improves navigation while retaining management JSON.
- Ignore all ordinary notes. This preserves scanning but leaves relevant user-supplied research unavailable to the established continuation workflow.

## Current state evidence

- Forward: `obsidian-finance/scripts/research_store.py` reads saved reviews and their publication markers.
- Reverse: `obsidian-finance/skills/finance-research/SKILL.md` establishes the selected root, issuer, cutoff and research publication contract.
- Error: `research_store._reviews` validates every child name as a managed identity before distinguishing an ordinary file.
- Data: the isolated Apple 2024Q3 dogfood reproduced `ambiguous identity` after saving a standalone Markdown; moving that single file outside the managed directory restored discovery.
- Boundary: structured progress, ordinary notes, and historical source evidence have distinct roles.

## Verification cases

- Add ordinary Markdown beside valid records. Verify discovery still succeeds, notes remain unchanged, and interrupted managed publication still reports its diagnostic.
- Save partial Apple analysis in one fresh dialogue and discover it in another. Verify prior content is preserved and remaining work and source links are discoverable.
- Supply an eligible note, a relevant note without verifiable timing, and an unrelated note. Verify the eligible claim can be cited, the missing timing is surfaced, and research progress does not change from note presence alone.

- In an isolated Apple pilot, save a Markdown-managed review after reading legacy inputs, interrupt a second save before publication, and retry from the last valid review with the draft preserved. Verify byte preservation of prior files, no newly written management JSON, acceptance of raw source JSON, and fresh-session discovery.
- Attempt two simultaneous saves from the same predecessor. Verify a single committed successor, a retained losing draft and an explicit conflict.
- Adopt a claim from an ordinary note with an eligible primary source. Edit that note and verify scoped reevaluation while the recorded claim and unrelated work remain available.
- Test a changed source or method, a late source and ordinary Markdown beside valid runs. Verify affected units require reevaluation, later evidence stays excluded, and unrelated research remains reusable.

- Render each note type from its own template and validate YAML syntax, required common and role-specific properties, consistent property types, and Obsidian rendering, including partial outputs and drafts. Verify plain user Markdown remains usable without mandatory metadata.
